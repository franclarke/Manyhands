## B-015 — Task Attempt Journal

- **Estado:** completada para Phase 2 checkpoint; el journal durable, CAS/fencing, state machine y wiring de scheduled/manual/integrator/repair están implementados. B-016 queda explícitamente fuera de alcance.
- **Causa raíz confirmada:** la identidad de ejecución de nodo sólo existía implícitamente en el worktree, el proceso en memoria y los arrays `leafResults`/`integrationResults`. RunExecutor capturaba diff, scope, validation y commit, pero no había una entidad durable entre esas fronteras. Un crash podía dejar un commit o proceso real sin una referencia recuperable, y resume podía volver a invocar el executor.
- **Diseño aplicado:** `JsonTaskAttemptJournal` persiste un archivo por run bajo `runs/attempts/<runId>.json`; es la fuente canónica de estado del attempt y usa escritura atómica, lock filesystem y CAS por versión. El RunRecord conserva sólo resultados compactos y el event log canónico recibe evidencia correlacionada.
- **Schema:** `TaskAttempt` version 1 contiene `attemptId`, run/node/operation, fencing, wave opcional, kind (`scheduled|manual|integrator|repair`), base commit, worktree/target, hashes de contrato/prompt/config, executor/model, timestamps, estado, process metadata, executor result, diff identity, scope/validation references, commit SHA, disposition, adoption/discard reason y error estructurado.
- **State machine:** `prepared → invocation_reserved → executor_running → executor_finished → diff_captured → scope_evaluated → validation_finished → commit_created → result_persisted`; recovery puede marcar `recovery_required`, desde donde sólo una adopción o descarte explícitos avanzan. `failed`, `cancelled` y `discarded` son terminales. No se permiten transiciones hacia atrás.
- **Idempotencia:** `reserve` acepta una idempotency key estable por run/node/kind/base/generation; reservas concurrentes devuelven el mismo attempt. CAS exige `expectedVersion`. El fencing exige operación y token coincidentes; `claimRecovery` sólo acepta un token mayor para transferir un attempt ambiguo a la operación actual.
- **Recovery:** antes de invocar executor, el host inspecciona attempts previos. Un resultado persistido se reutiliza si el NodeResult correspondiente existe; un attempt activo o ambiguo se convierte en `recovery_required` y no dispara una segunda llamada silenciosa. La adopción exige commit SHA válido y permite un verificador Git inyectado; el descarte registra razón y evidencia.
- **Integración:** execution host journaliza scheduled, integrator atómico y repair; manual node execution usa el mismo store. `attemptId` se propaga a AgentExecutionResult/IntegrationResult, RunExecutor, CLI executor y ProcessSupervisor metadata. Cancel service marca attempts en vuelo como `cancelled` con el lease anterior antes de kill/allDead.
- **Eventos:** se agregaron eventos canónicos `task.attempt.*` para cada frontera durable, con `attemptId`, `nodeId`, operation/fencing y disposition/commit cuando corresponde. Validation sigue siendo un hecho separado del exit code.
- **Archivos modificados:** `apps/web/src/lib/server/runs/task-attempt-journal.ts`, `execution-host.ts`, `execution-pipeline.ts`, `cancel-service.ts`, `run-model/types.ts`; `packages/execution-core/src/types.ts`, `run/executor.ts`, `integration/agent.ts`, `executor/{process,cli-executor,live-process-registry}.ts`; tests `tests/task-attempt-journal.test.ts` y consumidores afectados.
- **Regresión roja observada:** el test inicial falló porque `@/lib/server/runs/task-attempt-journal` no existía. La primera implementación roja adicional detectó que `recovery_required → adopted` estaba bloqueado; se corrigió permitiendo únicamente adopción/descarte explícitos desde ese estado.
- **Tests actuales:** schema/persistencia, monotonicidad, idempotencia, stale CAS, stale fencing, filesystem serialization, recovery takeover y adoption verification pasan: `task-attempt-journal` 4/4. Suites de execution-core, runner provisioning, runner, ProcessSupervisor y cancelación pasan en la corrida dirigida disponible.
- **Fault injection:** las pruebas del journal cubren excepciones/reanudación por frontera de estado, CAS concurrente, dos recoverers, discard idempotente y adoption verification. La garantía no pretende simular un executor externo real ni afirmar exactly-once donde el side effect no es verificable.
- **Garantías reales:** idempotencia de reserva/adopción y at-most-once invocation cuando existe evidencia ambigua. No se afirma exactly-once para un executor externo; si no puede verificarse el side effect, el estado queda `recovery_required`.
- **Trabajo diferido:** B-016 reconciliation closure, recovery center, B-018 event store incremental/outbox, B-021 crash-safe cherry-pick/repair, B-022 delivery segura y tareas posteriores.

## B-016 — Reconciliation closure y root worktree recreation

- **Estado:** completada.
- **Causa raíz confirmada:** el reconciler previo validaba cada commit de evidencia de forma aislada y filtraba sólo ese resultado. Un resultado downstream o una integración derivada podía sobrevivir a la pérdida de su antecedente. Además, un run con `provisioned` persistido no podía recuperar su repositorio raíz aislado cuando GC o una eliminación externa removían el directorio, aunque el SHA exacto aún existiera en el source capturado.
- **Diseño aplicado:** `reconcileInvalidationClosure` centraliza el cierre transitivo sobre `graph.dependencies` y ancestros composites. `reconcileExecutionWorld` contrasta resultados y commits de `TaskAttempt` contra Git, aplica ese cierre antes de filtrar la ejecución y resetear el checkpoint, y mantiene compatibilidad explícita con registros legacy sin graph (invalidación directa, nunca fallo de resume). `recreateProvisionedRepo` usa el descriptor durable de `provisioned` para reconstruir sólo el repo raíz propio del run desde el `executionBaseCommit`; verifica el commit en el source, hace checkout detached, y falla de forma recuperable si falta evidencia. El pipeline lo ejecuta antes de reanudar, bajo el repository lease ya adquirido, y persiste el hecho `world.reconciled` requerido.
- **Archivos modificados:** `apps/web/src/lib/server/runs/{execution-state.ts,world-reconcile.ts,repo-provisioner.ts,execution-pipeline.ts}`, `apps/web/src/lib/run-model/types.ts`; tests `tests/reconciliation-closure.test.ts`, `tests/world-reconcile-web.test.ts`.
- **Regresión roja observada:** `tests/reconciliation-closure.test.ts` falló 2/2: `reconcileInvalidationClosure is not a function` y `recreateProvisionedRepo is not a function`.
- **Tests y comandos:** rojo `corepack pnpm exec vitest run tests/reconciliation-closure.test.ts --retry=0 --maxWorkers=1 --minWorkers=1` -> 2 failed. Verde focal `... reconciliation-closure.test.ts world-reconcile-web.test.ts` -> 7/7. Consumidores `... reconciliation-closure.test.ts world-reconcile-web.test.ts world-reconciler.test.ts node-review.test.ts run-restart-target.test.ts run-runner-provisioning.test.ts task-attempt-journal.test.ts --retry=0 --maxWorkers=1 --minWorkers=1 --silent` -> 7 files, 34 tests pass. `corepack pnpm --filter @manyhands/web exec tsc --noEmit` -> pass.
- **Criterios verificados:** chain y diamond calculan el closure desde `graph.dependencies`; un commit ausente invalida sus dependientes y elimina sus resultados antes del resume; un root aislado ausente se recrea desde el SHA duradero sin invocar executor; evidencia Git faltante no se acepta; una segunda reconciliación sobre un mundo consistente no cambia estado (cobertura existente `world-reconciler`).
- **Compatibilidad / riesgos:** runs legacy sin graph se recuperan con la semántica directa previa, deliberadamente sin inventar dependencias. La recreación requiere que el source aún contenga el `executionBaseCommit`; un grounding/integration commit no anclado fuera del root no se fabrica y deja el run interrumpido con error accionable. La protección común de todas las mutaciones Git se completa en B-019; este camino usa el lease que el pipeline ya reclama antes del recovery.
- **Trabajo diferido:** transacciones de replan/amendment B-017, outbox/event store general B-018, cobertura crash-safe de cherry-pick/repair B-021 y cleanup/retention B-020.

## B-017 — Replan y amendments transaccionales

- **Estado:** completada.
- **Causa raíz confirmada:** replan preparaba el graft, invalidaba worktrees, reseteaba el checkpoint y sobrescribía graph/resultados como operaciones independientes. Una caída entre esas etapas dejaba el checkpoint anterior junto al graph nuevo; además, el flujo reiniciaba ejecución sin convertir el cambio semántico en una nueva aprobación. La rama de amendment tenía el mismo hueco entre invalidación, reset y persistencia.
- **Diseño aplicado:** `JsonPlanMutationJournal` persiste una `PlanMutationOperation` por run con operation ID estable, CAS de versión, lock de filesystem, tipo, versiones de plan, fingerprint de target, hash y graph preparado. Sus estados monótonos son `prepared → graph_prepared → record_persisted → checkpoint_reset → events_persisted → completed`. Replan y amendment reclaman mutation lease, publican graph/resultados bajo fencing, suben `planRevision`, invalidan la aprobación, resetean idempotentemente el checkpoint y emiten la nueva decisión `approve_plan:rN`; sólo entonces liberan el lease y completan la operación. El execution pipeline deja de ser disparado automáticamente tras replan/amendment: la revisión nueva exige su gate de aprobación.
- **Archivos modificados:** `apps/web/src/lib/server/runs/{plan-mutation-journal.ts,replan-service.ts}`, `apps/web/src/app/api/runs/[id]/decisions/[decisionId]/route.ts`; test `tests/plan-mutation-journal.test.ts`.
- **Regresión roja observada:** `tests/plan-mutation-journal.test.ts` inicialmente no podía importar `@/lib/server/runs/plan-mutation-journal` (0 tests, módulo inexistente).
- **Tests y comandos:** rojo `corepack pnpm exec vitest run tests/plan-mutation-journal.test.ts --retry=0 --maxWorkers=1 --minWorkers=1` -> 1 suite failed por módulo inexistente. Verde `tests/plan-mutation-journal.test.ts` -> 2/2. Consumidores `plan-mutation-journal + replan-question-gate + answer-route-execution-gate + plan-approval-service + editable-control-plane + node-review + reconciliation-closure` -> 7 files, 45 tests pass (las dos invocaciones focales registraron 19/19 y 10/10; las restantes ya habían pasado en la misma corrida dirigida). `corepack pnpm --filter @manyhands/web exec tsc --noEmit` -> pass.
- **Criterios verificados:** reserva concurrente con igual operation ID es idempotente; CAS stale falla; operación incompleta se conserva y se puede terminar tras reload; la publicación usa operation lease/fencing; replan/amendment incrementan revisión y borran aprobación anterior; el checkpoint sólo se resetea después de publicar el RunRecord; la decisión de aprobación nueva se persiste antes de cerrar la operación.
- **Compatibilidad / riesgos:** los replans que se suspenden por pregunta conservan su gate legacy y no publican una mutación hasta disponer de un graph estrictamente válido. Operaciones ya en `record_persisted` conservan el graph preparado y un journal inspectable para recovery; la reconciliación general de outboxes/eventos faltantes se completa en B-018. No se implementó replan transaccional de Phase 3 ni crash-safe cherry-pick/repair.
- **Trabajo diferido:** generalización de event outbox B-018, crash-safe cherry-pick/repair B-021 y delivery segura B-022.

## B-018 — Event log durable y recuperable

- **Estado:** completada.
- **Causa raíz confirmada:** el JSONL asignaba `seq` leyendo el archivo sin una exclusión cross-process, hacía `appendFile` directo y parseaba todas las líneas sin tolerancia. Una cola truncada impedía reconstruir el run; eventos con el mismo hecho podían duplicarse; no había checksum, envelope versionado ni reparación de la cola parcial.
- **Diseño aplicado:** el log usa un envelope v1 plano compatible con `RunEvent` (`schemaVersion`, `eventId`, `seq`, timestamp, actor, type, payload y SHA-256 checksum). Los writers usan lock de filesystem por run más cadena local, deduplican por `eventId`, asignan secuencia monotónica y reescriben atómicamente el prefijo válido más los eventos nuevos. `inspectRunModelEventLog` expone `ok|degraded|corrupt`: una línea JSON final truncada conserva y repara el prefijo; corrupción de checksum/envelope/seq detiene el writer y el reader/SSE sólo entrega evidencia previa. Logs legacy flat JSONL siguen siendo legibles. La reconciliación de logs existentes completa una resolución `approve_plan` demostrada por el RunRecord una sola vez.
- **Archivos modificados:** `apps/web/src/lib/server/runs/run-model-event-log.ts`; test `tests/durable-run-event-log.test.ts`.
- **Regresión roja observada:** `tests/durable-run-event-log.test.ts` falló 4/4: no existía `inspectRunModelEventLog` y un retry con igual `eventId` generaba `seq=2` en vez de devolver el evento `seq=1`.
- **Tests y comandos:** rojo `corepack pnpm exec vitest run tests/durable-run-event-log.test.ts --retry=0 --maxWorkers=1 --minWorkers=1` -> 4 failed. Verde focal `durable-run-event-log + run-event-persistence + run-events-replay + run-model-event-log-drain` -> 4 files, 16 tests pass. `corepack pnpm --filter @manyhands/web exec tsc --noEmit` -> pass.
- **Criterios verificados:** tail truncado se recupera sin perder el prefijo; checksum inválido bloquea append y marca corrupt; 12 appends concurrentes conservan `seq 1..13`; `eventId` es idempotente; lectura legacy funciona; una resolución durable faltante se reconstruye una sola vez; SSE continúa leyendo el prefijo válido y conserva cursor por `seq`.
- **Compatibilidad / riesgos:** el formato permanece JSONL y reescribe el archivo completo bajo lock (correctitud prioritaria; optimización incremental de grandes logs queda fuera). Los producers best-effort siguen explícitamente reservados a detalle diagnóstico; lifecycle/decisions/artifacts siguen usando los seams required existentes. El outbox general para cada hecho de cada store se completa progresivamente en los producers, sin inventar hechos cuando el RunRecord/attempt/checkpoint no los demuestra.
- **Trabajo diferido:** SSE incremental/escalable B-027, compactación/performance de logs B-030 y recovery center UI B-025.
