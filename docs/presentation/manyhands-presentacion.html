01 · Qué es ManyHands

Un pedido en lenguaje natural se convierte en trabajo verificable.

ManyHands toma un goal — el pedido, en lenguaje natural — lo descompone en un árbol de tareas con contratos explícitos, ejecuta cada tarea final en su propia copia aislada del repositorio, integra los resultados de abajo hacia arriba y deja todo registrado en un log de eventos que alimenta la interfaz.

No es «un agente que programa mejor»: es la estructura — copias aisladas del repo, contratos explícitos y un log de eventos — la que permite coordinar varios agentes sobre el mismo repositorio sin que se pisen entre sí.

flujo de trabajo evento persistido decisión humana

La frase para quedarse: goal → árbol de tareas con contratos → hojas en worktrees aislados → integración bottom-up → evidencia en el log.

02 · Qué problema resuelve

El problema no es pedirle más al agente. Es que falta estructura alrededor de él.

Estas tres fallas aparecen apenas dos o más agentes trabajan sobre el mismo repositorio real. Ninguna se arregla con mejor prompting — se resuelven con estructura verificable.

El síntomaQué hace ManyHandsEl mecanismo
Los agentes se pisan dos tareas tocan los mismos archivos a la vez y el resultado final es una mezcla que nadie diseñó. Cada tarea corre en su propia copia aislada del repositorio (un worktree), sobre su propia branch. Nada se mezcla hasta que el sistema decide integrarlo. mh/<run>/<task> + ScopeChecker
El agente dice «listo» y no lo está el agente termina y su output dice éxito, pero el repo no cambió lo que tenía que cambiar — o cambió otra cosa. El resultado no se decide por lo que dice el agente: se decide mirando el repo después — hay un cambio real, no toca archivos prohibidos, y pasa la validación del contrato. ResultRecorder.record → AgentResultStatus
Un crash deja todo ambiguo el proceso se cae a mitad de camino y no se sabe qué corrió, qué falta, ni si es seguro retomar. Cada paso queda anotado en un log antes de avanzar. Retomar un run no vuelve a ejecutar lo que ya corrió: reconstruye el estado exacto donde quedó. event log JSONL + checkpoints + decision.*

03 · La unidad de trabajo

La unidad básica no es un prompt: es un nodo de un árbol de tareas, con contrato y seams.

Un goal se descompone, un nodo a la vez, en un DAG (un árbol de dependencias sin ciclos): nodos compuestos que agrupan trabajo, y hojas — las unidades que un agente realmente ejecuta.

estructura padre → hijo dependencia de ejecución

Cómo se arma el árbol — recursivo, un nodo a la vez

decompose(nodo):
  veredicto = LLM(nodo.goal, rúbrica, seams heredados)

  si veredicto == "atómico":
      marcar nodo como hoja
      adjuntarle contrato + seams

  si veredicto == "decompose":
      generar hijos + seams que van a compartir
      para cada hijo: decompose(hijo)   // mismo criterio, recursivo

  si veredicto == "question":
      pedir aclaración humana

La rúbrica trae un parámetro de «agresividad» (coarse · balanced · fine · auto) que solo sesga qué tan grande puede ser una hoja «atómica» — no fija profundidad ni cantidad de nodos. Se retoma en la Parte II.

  • Contrato

    la frontera de ejecución de una hoja.

    Contract {
  objective: string
  acceptance: string[]          // qué significa "bien hecho"
  scope: {
    implementationPaths, testPaths, configPaths  // allow-list: guía
    forbiddenPaths                                // deny-list: siempre gana
  }
  validationCommands: Command[] // corren antes de aceptar la hoja
  consumes / produces: InterfaceContract[]  // seams
}
  • Seam

    una interfaz compartida (firma TS real) entre dos hojas. Se genera y se comitea antes de que las hojas empiecen a correr — por eso una hoja que consume un seam compila contra esa firma desde el minuto uno, sin esperar a que la otra termine.

  • Dependencia

    solo dice orden de ejecución — un concepto separado de la estructura del árbol y del seam. Dos hojas pueden compartir un seam sin depender una de la otra.

¿Y si dos hojas hermanas quieren tocar los mismos archivos? Eso no lo resuelve el contrato — lo resuelve el scheduler, en la slide 5.

04 · Ejecución y verificación

stdout explica. El diff decide.

El resultado de una hoja es siempre uno de estos estados — y el agente no elige cuál:

type AgentResultStatus =
  | "success"
  | "empty_diff"                    // no hubo cambios reales
  | "scope_violation"                // tocó un archivo prohibido
  | "validation_failed"              // el commit no pasó los tests
  | "executor_error" | "timeout"
  | "agent_committed_unexpectedly"   // el agente commiteó por su cuenta
  | "internal_error"
  1. ¿El proceso terminó bien, sin que el agente commiteara por su cuenta?

    un timeout o un commit no autorizado cortan acá — el agente nunca firma su propio resultado.

    timeoutagent_committed_unexpectedly
  2. ¿Hay un cambio real, y quedó dentro de lo permitido?

    si tocó un archivo prohibido, pierde sin importar el resto del diff; sin cambios, no hay nada que aceptar.

    empty_diffscope_violation
  3. El sistema hace el commit — recién ahí corren los tests.

    mh: <task> lo firma el orquestador; después corren los leafValidationCommands del contrato.

    validation_failedsuccess

Basado en packages/execution-core/src/result/recorder.ts — el commit ocurre antes de la validación, así que el repair (slide 5) siempre trabaja sobre estado auditable.

05 · Paralelismo e integración

El scheduler decide qué corre junto. El integrador decide cómo se combina.

La wave se decide en ejecución, no en planning: run.scheduling.wave_selected se persiste antes de cada dispatch.

  1. Riesgo alto o bloqueante entre dos tareas

    nunca corren en la misma wave.

  2. Sus archivos se superponen

    se serializan: una espera a que la otra termine.

  3. Falta contrato o scope declarado

    selección conservadora — se asume que sí chocan.

  4. Todo quedó bloqueado

    la wave nunca se cuelga: se sigue de a una.

Si el cherry-pick choca, el repair no adivina: recibe el objetivo del padre, las interfaces compartidas (seams) y los diffs de las hojas hermanas como contexto real. Presupuesto agotado → gate humano, con lo ya integrado preservado.

06 · Qué garantiza hoy y qué no

La fortaleza del sistema es que sus límites están explicitados en el propio modelo.

Esto no es «todo resuelto»: cada garantía de la izquierda ya apareció en un slide anterior — acá es el resumen. Los límites de la derecha son igual de explícitos.

GarantíaMecanismo que la sostiene
Aislamiento por tareaworktree mh/<run>/<task> + ScopeChecker con deny-wins.
Veredicto desde el repoResultRecorder: HEAD esperado → diff staged → scope → commit del orquestador.
Paralelismo auditadorun.scheduling.wave_selected persistido antes de cada dispatch.

UI sin estado inventadoJSONL → reducer → selectors; SSE con replay por cursor.
Recuperacióncheckpoints por thread + reconciliación del mundo físico al reanudar.

Límites actuales

  • Ejecuta CLIs externos autenticados; el runtime del agente no se controla, se contiene.
  • Persistencia single-machine: JSON/JSONL en disco, sin coordinación multi-host.
  • La validación vale lo que valgan los leafValidationCommands del contrato.

El fallo es visible, no escondido

  • Ocho estados tipados por hoja; nada termina en «falló algo».
  • Gates durables: la decisión sobrevive a un restart del proceso.

Esto es lo construido (Parte I). Lo que sigue es la propuesta para cerrar la tesis: qué falta, qué se propone concretamente y cómo se evaluaría.

07 · Parte II — Cierre de tesis

De perillas manuales a decisiones del sistema.

La Parte I mostró el sistema construido. La propuesta para cerrar la tesis: que tres parámetros de recursos que hoy ajusta el usuario a mano — les decimos «perillas» — pasen a ser decisiones del propio sistema, y medir con runs reales si eso mejora el resultado. El event log que ya existe es el instrumento de medición.

El resto de la charla, en tres pasos: 08 diagnostica el estado actual de las dos perillas que ya existen · 09 propone auto v2 para la primera · 10 el diseño para medir si funciona.

¿Por qué esto es tema de tesis y no una feature más? Los labs ya invierten en routing de modelos y control de esfuerzo a nivel de agente — la granularidad de descomposición para un enjambre de agentes está mucho menos explorada, y ManyHands es un vehículo raro para estudiarla: todo el pipeline (scheduler, integración, evidencia) es sensible al tamaño de las hojas.

08 · Estado actual

Las dos perillas ya existen. Las dos son heurísticas sin evidencia.

Ninguna decide todavía con datos: una es el modelo juzgándose a sí mismo; la otra es un cálculo determinista que nunca se calibró ni se conectó de verdad en producción.

Granularidad auto — en el decomposer

  • Dónde decide:

    un juicio LLM por nodo — ¿atómico o partir? — sesgado por una rúbrica de «unidad cohesiva». Sin targets de profundidad ni cantidad.

  • auto hoy:

    la rúbrica le dice al modelo «you choose»: autocalibra el umbral por nodo sin señales estructuradas del repo ni noción del costo de partir.

  • Ciudadano de segunda:

    el replan lo degrada a balanced; el event log lo registra como medium.

rúbrica de auto, v1 — cita literalstep-prompt.ts
auto: "whatever size matches THIS node's
  complexity — you choose. [...] Calibrate
  the split pressure per branch, not
  uniformly across the tree."

Routing por complejidad — en el executor

  • Scorer determinista y explicable:

    seams, archivos esperados, fan-in/out, scope y criterios → score → tier. Cada punto deja su señal legible.

  • Lanes por tier, con escalación:

    cada tier prefiere un modelo; si un repair reintenta, sube un tier («el retry merece un cerebro más fuerte»).

  • Nunca calibrado ni evaluado:

    pesos artesanales, y el camino productivo lo puentea: un run con selección fija de modelo no consulta al router.

resumen de tiers y lanes (paráfrasis)routing/complexity.ts · policy.ts
trivial   score ≤ 2   → haiku
standard  score ≤ 5   → sonnet
complex   score ≤ 9   → sonnet · opus
critical  score > 9   → opus
// repair: tier + 1 por intento

Ambas son heurísticas razonables para una v1 — ninguna decide con evidencia. Eso es exactamente lo que propone arreglar y medir auto v2 (slide 9).

09 · Propuesta

auto v2: que la decisión de atomicidad vea evidencia y costo, no solo el texto del goal.

«Atomicidad» es la pregunta que se repite en cada nodo del árbol (slide 3): ¿esta hoja ya es suficientemente chica, o conviene partirla de nuevo? Hoy esa pregunta la responde el modelo solo con el texto del goal.

Las ideas propuestas

  1. Prior determinista en planning.

    Función pura y testeable, misma filosofía que el scorer del routing; con señales del repository-index (imports, producer/consumer, superficie de API) produce una sugerencia de presión de split, con evidencia legible por nodo.

  2. Rúbrica consciente del costo.

    El modelo ve las dos fuerzas: hojas demasiado grandes fallan más; cada split agrega una integración y superficie de conflicto entre hermanos.

  3. Feedback del corpus (stretch).

    El event log ya registra timeouts, validaciones fallidas y conflictos de integración — señales de que una hoja estaba mal cortada. Cerrar ese loop queda declarado como extensión, no como compromiso del mes.

Cómo se implementa

  • El prior es una función pura → se desarrolla con TDD directo, sin LLM en los tests.
  • El canal ya existe: buildStepPrompt ya recibe hints del repo; agregar evidencia estructurada extiende un prompt builder que ya está testeado.
  • No toca executor, recorder, scheduler ni integración — el cambio queda acotado al decomposer.

Qué queda afuera, a propósito

  • Nada de RL ni fine-tuning: «frontier» acá significa decisión informada por evidencia y costo, no aprendizaje.
  • Routing v2 y esfuerzo de razonamiento quedan como extensión, no compromiso del mes.

10 · Evaluación

Cuatro brazos, cuarenta runs, y métricas que el sistema ya captura.

Un «brazo» es una política de granularidad fija para correr el mismo conjunto de features y comparar. random es el piso de control, no un rival serio.

BrazoQué responde
auto v2la contribución: ¿decidir con evidencia mejora el resultado?
auto v1¿cuánto aporta la evidencia sobre la rúbrica pelada?
balanced fijo¿la automatización iguala al mejor ajuste manual?
random por nodopiso de control: ¿la decisión importa siquiera?

4 brazos × 5 features × 2 repeticiones = 40 runs · 1 run por ventana de cuota (~5 h).

Corpus: 5 features que admitan cortes claramente distintos (~3 a ~12 hojas), con validación real ejecutable — diseñado y congelado antes de correr el primer brazo.

se mide con
GranularityVector por run: hojas, profundidad, éxito, conflictos, costo — ya emitido en run.metrics.ready.

Criterio de éxito: auto v2 iguala o supera al mejor ajuste manual por feature —sin conocerlo de antemano— a costo igual o menor, y domina claramente a random.
