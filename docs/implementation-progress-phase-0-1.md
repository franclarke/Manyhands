## Registro detallado

### B-001 — Aislar base y grounding

- **Causa raíz:** el provisioner de `localPath` trata el checkout fuente como repositorio de ejecución; grounding modifica el mismo path antes de crear worktrees de tareas.
- **Diseño aplicado:** el provisioner captura source repo/branch/SHA y crea un clone Git local, durable y separado por run. Los worktrees de hojas nacen dentro de esa copia. Se persisten `sourceRepoRoot`, `sourceBranch`, `sourceBaseCommit` y `executionBaseCommit`; legacy records se normalizan al leer. El patch final se calcula desde `sourceBaseCommit`, por lo que incluye grounding, y se materializa en la copia sin tocar el checkout fuente.
- **Archivos modificados:** `apps/web/src/lib/server/runs/repo-provisioner.ts`, `schema.ts`, `execution-state.ts`, `execution-pipeline.ts`, `final-apply.ts`; `tests/repo-provisioner.test.ts`, `final-apply.test.ts`, `run-runner-provisioning.test.ts`, `execution-state-repo-provision.test.ts`, `world-reconcile-web.test.ts`.
- **Tests agregados:** checkout dirty intacto ante una escritura/crash simulado de grounding; metadata source/execution persistida; artifact final incluye grounding y feature; final branch vive en el repo aislado.
- **Comandos y resultado:** regresión inicial `repo-provisioner.test.ts`: 1 fail esperado; luego 7/7 pass. Suite afectada `repo-provisioner`, `final-apply`, `execution-state-repo-provision`, `run-runner-provisioning`: 24/24 pass.
- **Riesgos pendientes:** fingerprint y resolución inmutable completa se cierran en B-008. Purge/retention de la copia durable se cierra con B-007 y fases posteriores. La copia local prioriza aislamiento; su costo en repos grandes queda fuera de Phase 0/1.

### B-002 — Checkpoints serializados y atómicos

- **Causa raíz:** `putWrites` realiza read-merge-write concurrente y todos los writes usan `writeFile` directo.
- **Diseño aplicado:** una cadena de escritura compartida por directorio/thread serializa `put`, `putWrites` y `deleteThread`, incluso entre instancias del saver en el mismo proceso. Cada archivo se escribe en un temp exclusivo, se hace `sync`, se cierra y se publica por `rename`. Antes de escribir se limpian `.tmp` huérfanos. Pending writes se deduplican por `taskId + channel`, de modo que un retry no duplica resultados.
- **Archivos modificados:** `packages/orchestrator-graph/src/checkpointer.ts` y `checkpointer.test.ts`.
- **Tests agregados:** 500 pending writes concurrentes; retry idempotente; recuperación/limpieza de temp huérfano. Se reejecutaron corruption tests y planning/execution graph resume.
- **Comandos y resultado:** regresión inicial: 3 tests fallaron (1/500 writes, duplicado y temp persistente). Después: `checkpointer` + corruption 16/16; conjunto checkpointer/corruption/planning graph/execution graph 37/37; `pnpm -F @manyhands/orchestrator-graph typecheck` pasó.
- **Riesgos pendientes:** la exclusión cross-process fuerte requiere un storage/lease interproceso y se mantiene como trabajo de Phase 2; la atomicidad de rename se verificó en Windows en el stress local.

### B-003 — Mutation lease/fencing

- **Causa raíz:** CAS existe en algunas rutas, pero background writers y transiciones guardan snapshots completos sin demostrar ownership de la operación.
- **Diseño aplicado:** se extendió el seam de mutación existente con `operationId`, tipo de operación, lease activo y fencing token monotónico persistidos. Planning, execution, resume, manual node execution, hosts, heartbeat y watchdog escriben bajo el lease; cancel lo invalida antes de abortar. Un resultado que vuelve después de cancelación se descarta. `saveRunWithRequiredStatusEvent` usa CAS por versión y no puede hacer rollback sobre una versión nueva. El `JsonRunRecordStore` serializa además el read-modify-write entre instancias mediante un mutex corto de filesystem con owner/token, recuperación de owner muerto y release verificado.
- **Archivos modificados:** `schema.ts`, `repository.ts`, `mutation-guard.ts`, `run-operation-lease.ts`, `audited-mutation.ts`, `planning-pipeline.ts`, `planning-host.ts`, `execution-pipeline.ts`, `execution-host.ts`, `runner-heartbeat.ts`, `runner-watchdog.ts`, cancel route; tests de operation lease, repository, cancel y runner.
- **Tests agregados:** restart contra old runner; cancel-vs-complete; watchdog-vs-complete; release tardío; fence monotónico ante snapshot restaurado; 100 mutaciones concurrentes desde dos instancias; cancel invalida el lease; resultado tardío del engine no se persiste.
- **Comandos y resultado:** regresiones rojas confirmadas para módulo ausente, stale completion y stores independientes (incluido `EPERM` por `rename` concurrente en Windows). Matriz afectada final: 62/62 assertions; `pnpm --filter @manyhands/web typecheck` pasó.
- **Riesgos pendientes:** el outbox general, task-attempt identity y reconciliation post-crash pertenecen a Phase 2. El mutex de mutación es deliberadamente corto y distinto del repo lease de larga duración, que se endurece en B-004.

### B-004 — Repo lock atómico

- **Causa raíz confirmada:** el takeover stale era read → rm → create no atómico: dos contendientes podían leer el mismo owner stale, el `rm` rezagado de uno borraba el lock recién creado del otro y ambos terminaban con `acquired=true`. El release era read-then-remove keyed solo por `runId`, por lo que un release tardío de una encarnación anterior del mismo run borraba el lock vigente. No había token inmutable, generación de fencing, heartbeat del lock ni keying por git common dir (dos paths al mismo repo — p.ej. un worktree — obtenían locks separados).
- **Diseño aplicado:** el lock es un **directorio** creado con `mkdir` atómico; `owner.json` (inmutable) lleva `runId`, `pid`, `token` random y `generation` monotónica persistida (`run.lock.generation`, escrita por el ganador bajo exclusión). El takeover stale re-verifica el owner inmediatamente antes de un `rename` a quarantine (solo un rename gana; el resto observa ENOENT y vuelve a competir por el `mkdir`); el ganador fresco verifica su token con read-back antes de entregar el lease. Liveness es heartbeat-first: archivo `heartbeat-<token>.json` renovado por `startRepoLeaseHeartbeat`; PID y heartbeat del RunRecord son solo fallback (nunca la única señal). `renewRepoLease`/`releaseRepoLease`/`assertRepoLeaseCurrent` verifican token (+generation en fencing); un release que perdió una carrera con un takeover restaura a la víctima. Keying: `git rev-parse --git-common-dir` con realpath; en repos git el lock vive **dentro** de `.git/manyhands/` (el porcelain del checkout fuente queda limpio, invariante B-001); paths no-git usan `<path>/.manyhands/`. Pipeline: el lease se adquiere **antes** del clone de provisioning (primer side effect git sobre el source), se renueva en background y se fencea con `assertRepoLeaseCurrent` antes del final apply en ambos engines; `runNodeExecutionPipeline` (ejecución manual) ahora también adquiere/libera el lease.
- **Archivos modificados:** `apps/web/src/lib/server/runs/repo-lock.ts` (rewrite), `apps/web/src/lib/server/runs/execution-pipeline.ts` (claim antes de provision, heartbeat, fencing, release por lease en start/resume/manual), `tests/repo-lock-atomic.test.ts` (nuevo), `tests/repo-lock.test.ts` (API por lease).
- **Tests agregados:** token/generation monotónica; release tardío de encarnación previa del mismo run; release vs takeover con restore; 12 contendientes fresh concurrentes; 16 contendientes × 6 rondas sobre lock stale (exactamente un owner válido y owner on-disk == token del ganador); lock legacy formato archivo (honrado vivo, robado stale); lock corrupto; renew token-checked; heartbeat periódico con stop; liveness heartbeat-first con PID muerto real (child spawneado); fencing con RepoLeaseLostError tras takeover y tras release; keying por common dir con `git worktree` real; residuo de crash (dir sin owner.json) robado tras grace window.
- **Comandos ejecutados y resultados:** regresión inicial `pnpm vitest run tests/repo-lock-atomic.test.ts` → 12 failed / 1 passed (rojo esperado: API ausente). Tras implementación: 13/13 pass. `tests/repo-lock-atomic.test.ts + tests/repo-lock.test.ts + tests/run-runner-provisioning.test.ts` → 31/31 (la primera corrida falló 1: el generation file ensuciaba el porcelain del source — se movió el lock a `.git/manyhands/`, verde después). Consumidores del pipeline `run-runner.test.ts, run-start-cas.test.ts, node-run-contract-boundary.test.ts, cancel-route.test.ts` → 16/16. `pnpm web:typecheck` → pasa.
- **Riesgos pendientes / desviaciones:** (1) el stress **multiproceso** real quedó diferido: el harness no puede spawnear el módulo TS de apps/web en children sin tooling extra; la atomicidad de `mkdir`/`rename` es a nivel kernel y el stress in-process ejercita los mismos interleavings de syscalls — se recomienda un smoke multiproceso en Phase 2 junto con RK-02. (2) Existe una ventana teórica microscópica donde un takeover con juicio stale muy viejo puede quarantinar un lock recién ganado; se mitiga con re-check pre-rename + read-back verify del ganador, y el fencing por token/generation garantiza que un lease fantasma jamás pasa `assertRepoLeaseCurrent` (la propiedad "un solo owner **válido**" se sostiene por construcción). (3) Locks legacy en `<sourceRoot>/.manyhands/run.lock` de versiones previas dejan de consultarse (el path nuevo está en `.git/manyhands/`); son residuo inerte. (4) Delivery/cleanup/workspace bootstrap siguen fuera del lease: es exactamente B-019 (Phase 2) y B-022 (Phase 3).
- **Dependencias habilitadas:** B-005 (cancel puede invalidar el repo lease), B-007 (purge bajo repo lease), B-019/B-022.

### B-005 — Cancelación realmente terminal

- **Causa raíz confirmada:** el supervisor existía solo para el executor principal (`spawnExecutorProcess` registraba con `processOwnerId`); planning/decomposer, titler, validation runner, dependency installer, git de final apply, clone de provisioning y terminales spawneaban sin registro, owner ni señal. El cancel route transicionaba directo a `interrupted` y respondía 200 aunque `killReport.allDead === false`.
- **Diseño aplicado:** (1) **ProcessSupervisor**: `superviseChildProcess(meta {runId, label, operationId?}, child, {signal?, spawnFn?})` en `live-process-registry` de execution-core — registra bajo el run con metadata, cablea AbortSignal→tree kill, auto-desregistra en `close` (handles pty via disposer explícito); `KillVerification` ahora lleva `label`/`operationId`. (2) **Cobertura**: validation runner (`ValidationRunContext.supervision`, aborta con exit 130 si el signal ya está abortado), dependency installer (`ensure({cwd, supervision})`, timeout ahora mata el **árbol**), decomposers CLI (`PickDecomposerInput.spawn` inyectado por planning-host con `supervisedSpawnFn`), titler (spawn supervisado desde planning-pipeline), git de final-apply y clone del provisioner (contexto ambiente `runWithProcessSupervision` + `supervisedExecFile` — cubre todo el árbol de helpers sin tocar cada firma), terminal sessions (pty y fallback child registrados bajo el run), run-level validation del execution-host (supervision con operationId del lease). (3) **`cancelling`**: nuevo status; `cancelRun` (cancel-service, inyectable) claimea `cancelling` invalidando el lease (fencing B-003), aborta, mata y verifica; **solo** `allDead=true` hace GC de worktrees y transiciona a `interrupted`; con survivors el run permanece en `cancelling` (route responde 202 con survivors etiquetados) y el retry de cancel está permitido desde `cancelling` y completa el trabajo. GC nunca corre con survivors (podrían tener cwd en los worktrees). `run.cancelled` lleva `allDead`.
- **Archivos modificados:** `packages/execution-core/src/executor/{live-process-registry,kill}.ts`, `validation/{runner,dependencies}.ts`, `run/executor.ts`, `integration/agent.ts`; `apps/web/src/lib/server/runs/{process-supervision (nuevo), cancel-service (nuevo), terminal-sessions, execution-pipeline, execution-host, planning-pipeline, planning-host, final-apply, repo-provisioner, schema, lifecycle}.ts`; `apps/web/src/app/api/runs/[id]/cancel/route.ts`; `apps/web/src/lib/{api-types,status,decomposer-policy}.ts`, `run-model/{types,run-phases}.ts`; tests `tests/process-supervisor.test.ts`, `tests/cancel-terminal.test.ts` (nuevos).
- **Tests agregados:** primitive del supervisor (meta en kill report, auto-unregister, abort→tree kill con child real); validation runner registrado y muerto por `killOwnedProcessTrees` con comando real de larga vida + señal pre-abortada; installer con child real; `supervisedSpawnFn`; terminal registrada y muerta con el run; `cancelRun` con survivors (permanece `cancelling`, lease invalidado, sin GC) → retry limpio → `interrupted`; kill limpio en un paso; fase correcta en `interruptedDuring`; GC solo con allDead.
- **Comandos ejecutados y resultados:** regresión inicial roja (módulos ausentes). Post-implementación: `process-supervisor + cancel-terminal + cancel-route + repo-lock-atomic + run-runner-provisioning + run-runner + run-start-cas + node-run-contract-boundary + terminal-sessions-registry` → 48/48; `decomposer-codex-recursive + run-titler` → 12/12; `pnpm -F @manyhands/execution-core typecheck` → pasa; `pnpm web:typecheck` → pasa.
- **Riesgos pendientes / desviaciones:** (1) el registry es in-memory: tras un crash del server, un retry de cancel reporta `allDead` vacuamente aunque queden huérfanos OS — requiere journal durable de attempts/procesos (Phase 2, B-015). El sweeper no toca `cancelling` (auto-promoverlo violaría la invariante); el camino de salida es el retry de cancel. (2) Eventos run-model no-status emitidos por el host in-process entre cancel y propagación del abort no se fencean todavía; los writes de RunRecord sí (B-003) — el fencing de eventos llega con el outbox de B-013/B-018. (3) `runNodeExecutionPipeline` y validation dentro de `RunExecutor` pasan supervision con runId (kill cubierto); el AbortSignal no llega aún a cada capa interna del RunExecutor para validation — la terminación está garantizada por el kill verificado, no por cortesía cooperativa. (4) UI: `cancelling` se presenta como "blocked" (badge) y el canvas vacío como interrupted; el recovery center completo es B-025 (Phase 4).
- **Dependencias habilitadas:** B-007 (active ⇒ cancel primero, con verificación real), B-013 (eventos nativos con supervisor como fuente), B-015 (attempt journal).

### B-006 — Boundary local seguro

- **Causa raíz confirmada:** no existía frontera alguna: sin bind a loopback declarado, sin validación de Host/Origin, sin token de sesión (CF-08); la file API seguía symlinks/junctions fuera del root (CF-40 — containment solo léxico); las rutas de terminal ignoraban el run del path (CF-41 — el terminalId global era capability suficiente); executors y terminales heredaban `process.env` completo (CF-28).
- **Diseño aplicado:** (1) **Boundary**: evaluador puro `evaluateRequestBoundary` (`lib/server/security/boundary.ts`) — Host allowlist loopback (+`MANYHANDS_ALLOWED_HOSTS`), Origin allowlist (rechaza `"null"` y todo origin no-loopback), capability de sesión requerida para toda mutación de API y para SSE (`events`/`run-events`), terminal, `workspace-file`/`workspace-tree` y `export`; `middleware.ts` lo aplica a cada request; token = `MANYHANDS_SESSION_TOKEN` (launcher) o aleatorio por boot, distribuido al UI local como cookie `mh_session` SameSite=Strict (el UI no necesita cambios) y como header `x-manyhands-session` para scripts. Bind por defecto `-H 127.0.0.1` en `next dev/start` (`dev:lan` = opt-in). El launcher genera el token, lo comparte con el server y lo usa en su propio monitor. (2) **Containment**: `resolveContainedWorkspaceFile` compara realpath del target contra realpath del root; `workspace-file` y `workspace-tree` responden 403 (`WorkspaceEscapeError`) ante symlink/junction escape. (3) **Ownership**: `getTerminalSessionForRun`/`closeTerminalSessionForRun`; input/resize/stream/delete responden 404 cross-run. (4) **Env allowlist**: `buildAgentEnvironment` (execution-core) — sistema/toolchain + HOME/APPDATA (auth stores CLI) + credenciales de provider declaradas (solo agentes; excluidas en terminales) + `MANYHANDS_AGENT_ENV_ALLOW`; aplicado al spawn del executor (`process.ts`), a terminales (pty y fallback) y los decomposers/titler ya pasan por spawn supervisado. ### B-007 — Archive/purge seguro

- **Causa raíz confirmada:** `DELETE /api/runs/[id]` era CRUD puro: `repository.delete` borraba el JSON sin exigir status inactivo, sin cancelar procesos y sin limpiar events/checkpoints/worktrees — run fantasma con runner vivo y artifacts huérfanos (CF-05).
- **Diseño aplicado:** `archive-service.ts` con dos operaciones. **Archive** (lógico): `archivedAt` en el RunRecord vía `claimRunMutation` (CAS); rechazado con 409 si el run está activo (`generating/running/paused/cancelling`) o con runner vivo; el listado (`GET /api/runs`) oculta archivados salvo `?include=archived`; `unarchiveRun` disponible. **Purge** (físico): solo para statuses inactivos, exige `!isRunnerActive` y `countLiveProcesses(runId)===0` (supervisor de B-005), claimea una operación `purge` (lease/fencing de B-003, kind ya pre-declarado), y ejecuta pasos journaled en `<runsDir>/<runId>.purge.json`: (1) work copy del run — **solo** si vive bajo el work root gestionado (`resolveManyhandsPath("work")`); un `provisioned.repoRoot` legacy que apunte a un repo del usuario solo pierde `.manyhands/worktrees/<runId>`, jamás el repo; (2) checkpoints de ambos threads (`runId` y `planningThreadId(runId)`); (3) event log JSONL; (4) **último** la metadata; después se borra el journal. Crash en cualquier paso deja journal + metadata → el retry converge (pasos `done` se saltean); purge de un run ya inexistente limpia el journal residual y devuelve `alreadyPurged`. `DELETE` = archive; `DELETE ?purge=1` = purge.
- **Archivos modificados:** `apps/web/src/lib/server/runs/archive-service.ts` (nuevo), `schema.ts` (`archivedAt`), `apps/web/src/app/api/runs/[id]/route.ts` (DELETE), `apps/web/src/app/api/runs/route.ts` (filtro archived).
- **Tests agregados (`tests/archive-purge.test.ts`):** DELETE de run activo → 409 e intacto; archive de inactivo → 204, metadata con `archivedAt`, lista lo oculta / `include=archived` lo muestra; purge de activo rechazado; purge con proceso vivo registrado rechazado; purge feliz elimina work copy + checkpoints (ambos threads reales) + events + metadata + journal y es idempotente; work copy fuera del root gestionado nunca se borra (repo del usuario preservado); crash inyectado a mitad de purge conserva metadata+journal y el retry converge.
- **Comandos ejecutados y resultados:** regresión inicial: módulo ausente (rojo). Post-implementación: `archive-purge` 7/7; + `run-record-repository`, `run-create-route`, `cancel-terminal` → 30/30; `pnpm web:typecheck` → pasa.
- **Riesgos pendientes / desviaciones:** (1) el user pidió "purge solo para runs terminales"; `isTerminalStatus` excluye `interrupted`/`created`/`needs_review`/`approved`, que no pueden cancelarse ni terminarse — purge estrictamente terminal los haría imborrables. Se implementó purge para **cualquier status inactivo** con las tres guardas duras (sin runner, sin procesos, lease); la invariante de aceptación de la auditoría ("no se elimina metadata mientras quede runner/proceso/worktree activo") se cumple estrictamente.
