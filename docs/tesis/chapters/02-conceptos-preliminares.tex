\chapter{Conceptos preliminares}
\label{cap:preliminares}

Este capítulo introduce los conceptos necesarios para comprender el diseño de
ManyHands. El propósito no es agotar cada tema, sino establecer un vocabulario
común para explicar cómo se coordinan agentes, código y evidencia.

\section{Agentes de código}

Un agente de código combina un modelo de lenguaje con herramientas que le
permiten observar y modificar un entorno de desarrollo. Su operación puede
entenderse como un ciclo de cuatro pasos \cite{yao2023react,wang2024survey}:

\begin{enumerate}
  \item observa archivos, estructura y resultados de comandos;
  \item interpreta el objetivo y decide una acción;
  \item edita código o ejecuta una herramienta;
  \item usa el resultado para continuar o corregirse.
\end{enumerate}

Este ciclo explica por qué un agente puede resolver errores de compilación sin
intervención constante. Sin embargo, no establece por sí mismo qué archivos
puede tocar, cómo se coordina con otros agentes ni qué prueba demuestra que su
trabajo es correcto. ManyHands agrega ese plano de control alrededor de los
ejecutores existentes.

\section{Grafos de tareas}

Un grafo dirigido acíclico o DAG es un conjunto de nodos unidos por relaciones
dirigidas sin ciclos. La ausencia de ciclos permite ordenar las tareas: si
$A \rightarrow B$, entonces $A$ debe producir algo antes de que $B$ pueda
continuar. Los nodos que no dependen entre sí forman una \emph{frontera} y
pueden ejecutarse al mismo tiempo.

En software, una única flecha de dependencia resulta ambigua. Dos tareas pueden
estar relacionadas porque una consume el archivo de la otra, porque comparten
una interfaz o simplemente porque pretenden escribir el mismo recurso. Estas
situaciones producen efectos distintos: espera, paralelismo coordinado o
exclusión mutua. Por esa razón ManyHands utiliza relaciones tipadas, descritas
en el capítulo~\ref{cap:arquitectura}.

\section{Diseño por contratos}

El Diseño por Contratos propone que la colaboración entre componentes se base
en obligaciones explícitas, no en supuestos implícitos \cite{meyer1992dbc}. En
un sistema con modelos generativos este principio es especialmente útil: el
modelo puede interpretar lenguaje natural, pero la ejecución necesita límites
que un programa pueda validar.

ManyHands aplica contratos en cuatro dimensiones:

\begin{itemize}
  \item \textbf{alcance}: qué rutas puede modificar una unidad;
  \item \textbf{interfaz o costura}: qué firma comparten productor y
  consumidores;
  \item \textbf{artefacto}: qué resultado material debe producirse;
  \item \textbf{validación}: qué comportamiento debe comprobarse y con qué
  evidencia.
\end{itemize}

Un contrato no garantiza que el agente escriba código correcto, pero convierte
una expectativa difusa en una condición observable. También permite detectar
incompatibilidades antes de consumir tiempo de ejecución.

\section{Aislamiento mediante Git worktrees}

Ejecutar varios agentes sobre el mismo directorio produciría condiciones de
carrera y dificultaría atribuir cada cambio. Git ofrece los \emph{worktrees}:
directorios de trabajo independientes que comparten la base de objetos del
repositorio, pero poseen índice y \texttt{HEAD} propios \cite{chacon2014pro}.

El worktree evita interferencias entre cambios, pero no constituye por sí solo
un sandbox de seguridad. ManyHands lo complementa con control de rutas,
credenciales acotadas y supervisión de procesos. La separación conceptual es
importante: el worktree protege la composición de código; el sandbox limita las
capacidades del proceso.

\section{Verificación basada en evidencia}

La salida textual de un agente no es una prueba de corrección. La ingeniería de
software utiliza compiladores, tests e integración continua para evaluar el
artefacto observable \cite{humble2010continuous,beck2002tdd}. ManyHands lleva
este principio a una cadena de evidencia asociada a identidades Git:

\begin{enumerate}
  \item cada resultado se vincula al commit candidato exacto;
  \item cada criterio se asocia con una obligación de validación;
  \item se conserva el comando, su salida y su huella;
  \item cuando corresponde, un control negativo comprueba que la prueba detecta
  realmente la ausencia del cambio.
\end{enumerate}

La Matriz de Evidencias resume estas relaciones. Su función no es sustituir el
juicio de producto, sino impedir que un estado verde pierda trazabilidad sobre
qué se probó y sobre qué versión.

\section{Eventos como historia canónica}

En Event Sourcing el estado no se guarda únicamente como una fila mutable, sino
como una secuencia de hechos de solo anexión \cite{fowler2005event,helland2007life}.
Si $e_1,\ldots,e_n$ son los eventos de un run, su estado se reconstruye mediante
una función reductora:

\begin{equation}
S_n = \operatorname{fold}(S_0,[e_1,e_2,\ldots,e_n]).
\label{eq:event-sourcing}
\end{equation}

El journal registra hechos como la creación del run, el inicio de un intento,
la adopción de un artefacto o la publicación final. Las pantallas y snapshots
son proyecciones derivadas. Esta separación permite recuperar el sistema tras
un reinicio, distinguir evidencia canónica de trazas diagnósticas y explicar
con precisión cómo se alcanzó un resultado.
