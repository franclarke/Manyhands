\chapter{Estado del arte}
\label{cap:estado}

ManyHands se ubica en la intersección entre agentes de programación,
orquestación multi-agente, grafos de tareas e ingeniería de software basada en
evidencia. Esta sección resume qué aporta cada línea y qué problema permanece
abierto cuando se combinan sobre repositorios reales.

\section{Agentes individuales de programación}

SWE-bench consolidó una forma exigente de evaluar agentes: resolver incidencias
históricas en repositorios reales y comprobar los parches mediante pruebas
\cite{jimenez2024swebench}. SWE-agent mostró además que la interfaz disponible
para navegar y editar el repositorio influye fuertemente en el desempeño del
modelo \cite{yang2024sweagent}. Herramientas como Codex CLI y Claude Code
continúan esta línea mediante ciclos de inspección, edición y prueba.

Estas herramientas son adecuadas como \emph{ejecutores}: reciben un objetivo y
operan sobre un entorno. No resuelven necesariamente la gobernanza de varios
intentos concurrentes, la propiedad de interfaces compartidas o la integración
jerárquica. ManyHands las utiliza como componentes dentro de un plano de
control, en lugar de competir con su capacidad generativa.

\section{Sistemas multi-agente conversacionales}

ChatDev y MetaGPT distribuyen roles como producto, arquitectura, desarrollo y
pruebas entre agentes que intercambian mensajes y documentos
\cite{qian2024chatdev,hong2024metagpt}. Su aporte principal es mostrar que la
especialización de roles puede estructurar la generación de software.

La conversación, sin embargo, es una representación débil para coordinar
cambios físicos. Una frase como ``el módulo A provee usuarios'' no fija una
firma, una ruta ni una versión. Dos agentes pueden compartir la intención y aun
así producir implementaciones incompatibles. ManyHands conserva la semántica
en lenguaje natural durante la planificación, pero la compila a contratos y
relaciones que el software puede verificar.

\section{Grafos y paralelismo}

LLMCompiler representa llamadas a herramientas mediante un DAG y ejecuta en
paralelo aquellas cuyos datos de entrada ya están disponibles
\cite{kim2024llmcompiler}. El principio es aplicable a agentes de código, pero
el artefacto intercambiado ya no es sólo un valor: puede ser un conjunto de
archivos, una interfaz pública o un commit.

Por ello, un grafo de software necesita distinguir tres preguntas: si una tarea
consume el resultado de otra, si ambas pueden trabajar contra un contrato
común, y si pretenden escribir el mismo recurso. ManyHands expresa estas
preguntas mediante relaciones distintas, de modo que el scheduler no confunda
dependencia funcional con conflicto de escritura.

\section{Asignación de modelos y granularidad}

FrugalGPT y RouteLLM estudian cómo dirigir una consulta hacia un modelo que
equilibre calidad y costo \cite{chen2023frugalgpt,ong2024routellm}. Esa decisión
responde \emph{qué modelo} debe atender una unidad. La política de granularidad
de esta tesis responde una pregunta anterior: \emph{qué cantidad de trabajo}
debe constituir una unidad. Ambas estrategias son complementarias.

La tabla~\ref{tab:estado-del-arte} resume el foco de cada enfoque. No pretende
establecer una competencia de rendimiento, sino ubicar el aporte arquitectónico
de la tesis.

El aporte distintivo de ManyHands es combinar tres ideas que suelen aparecer
separadas: descomposición explicable, coordinación mediante contratos y entrega
respaldada por evidencia sobre el commit exacto. El resultado es un plano de
control orientado a la ingeniería del proceso, no un nuevo modelo generativo.
