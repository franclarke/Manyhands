Contexto y Motivación

La Brecha: De Parches Aislados a Repositorios Reales

SWE-bench (Paradigma Actual)

Parche Atómico Aislado

• 1 solo archivo modificado
• Contexto acotado (~15k tokens)
• Sin dependencias cruzadas ni concurrencia
• Generación directa de un archivo .patch

ManyHands (Esta Tesis)

Objetivo de Repositorio Completo

• Múltiples capas (UI, API, Dominio, Base de Datos)
• Contexto masivo (>150k tokens)
• Riesgo de colisiones de escritura y regresiones
• Resuelto con Grafo de Contratos y Verificación

⚠️ El Problema: Al escalar a repositorios reales, un agente monolítico satura su contexto y produce deriva semántica.

Problema Fundamental

La Paradoja de la Granularidad

Sub-división (Monolito)

Un Solo Agente

• Saturación de Contexto: Alucinación de interfaces.
• Deriva de Alcance: Modifica código no autorizado.
• Punto Único de Fallo: Todo o nada.

Sobre-división (Micro-fragmentación)

Demasiados Agentes

• Explosión de Interfaces: N² costuras que coordinar.
• Sobrecosto de Coordinación: Esperas y mensajes.
• Conflictos de Merge: Colisiones al integrar ramas.

🎯 Solución ManyHands: Granularidad adaptativa fundamentada en reglas categóricas (dividir solo cuando existe justificación).

Formulación Científica

Capítulo 3: Estado del Arte

¿Por qué falla el paradigma actual?

SWE-agent (Princeton)

Agente Monolítico

• 1 solo agente por issue.
• Sin aislamiento en disco.
• Entrega un .patch ciego sin verificar falsabilidad.

MetaGPT / ChatDev

Coordinación por Chat

• Diálogo libre en lenguaje natural.
• Acumula deriva semántica.
• Sin contratos tipados ni contención de SO.

ManyHands (Esta Tesis)

Orquestación Formal

• Grafo Híbrido con contratos Zod.
• Git Worktrees + ScopeGuard.

Capítulo 5: Arquitectura Central

El Run: Unidad Central de Producto

★ Event Sourcing Determinista: El Run no es un chat efímero; cada transición es un evento inmutable registrado en RunStore.

Estructura Topológica

El Grafo Híbrido y sus 4 Relaciones Tipadas

Jerarquía

1. parentId

Ownership e integración ascendente en el árbol de dependencias.

Flujo de Datos

2. ArtifactReq

Dependencia física serializada ($A \to B$) basada en archivos.

Paralelismo

3. SeamBinding

Habilita paralelismo ($A \parallel B$) fijando contratos de interfaz antes de escribir código.

Concurrencia

4. ResourceClaim

Exclusión mutua sobre el mismo archivo para evitar lost updates.

🔹 Jerarquía de 3 Niveles: Raíz (Goal) $\longrightarrow$ Composites (Integración) $\longrightarrow$ Hojas (Ejecución aislada).

Control Formal

Grounding Presupuestado y Verificación Estática

Grounding del Repositorio

RepositoryIndex

• Vistas indexadas con presupuesto acotado (tokens, llamadas).
• Digest criptográfico SHA-256 (previene bucles causales).
• El modelo solo ve lo estrictamente necesario para planificar.

Compilador de Grafos

verifyPlan (8 Invariantes)

• Aciclicidad: Sin ciclos en dependencias.
• Preservación: No se pierden criterios de aceptación.
• Disyunción: Escritores concurrentes aislados.
• Cobertura: Toda hoja posee suite probatoria.

✓ Ningún plan se ejecuta sin superar los 8 invariantes estáticos de compilación.

Capítulo 4: Granularidad · Aporte del Eje 2 (20%)

El Fracaso del Scoring Continuo ($C_{task}$)

Evaluación sobre 83 Casos Reales

Fórmula Legacy Adimensional

$$C_{task}(u) = w_1 S_r + w_2 I_i + w_3 V_s + w_4 T_m > \theta$$ • Carece de significado físico (sin unidades de tiempo ni tokens).
• Degeneración del Umbral: Variar $\theta \in [0, 0{,}20]$ produjo exactamente las mismas decisiones en el 100% de los casos.

Aporte Científico

El Resultado Negativo Demostrado

• La granularidad no es una optimización continua en $\mathbb{R}$.
• Es una decisión discreta y estructurada gobernada por razones arquitectónicas de software.

💡 Conclusión: El scoring numérico opaco debe reemplazarse por una política categórica determinista.

Aporte del Eje 2

Política de Granularidad Categórica 4.0

Razón 1

doesNotFit

Capacidad: Supera límites de tokens (>24k), rutas en alcance (>40) o archivos a crear (>12).

Razón 2

runsInParallel

Concurrencia: Módulos ortogonales con interfaces desacoplables mediante SeamContract.

Razón 3

verifiableApart

Aislamiento Probatorio: Suites de tests independientes ejecutables por separado.

🎯 Si cumple al menos una razón $\implies$ Subdividir. Si no $\implies$ Ejecutar como Hoja Cohesiva.

Aplicación Práctica

Caso de Estudio: Paralelismo por Contrato

Backend (Worker 1)

API REST & Token Verifier

• Implementa endpoint POST /api/auth/google.
• Valida JWT y persiste sesión en base de datos.
• Respeta la firma estricta del SeamContract.

Frontend (Worker 2)

UI & Callback Handler

• Implementa botón de Login y pantalla de callback.
• Consume el payload declarado en el contrato.
• Se desarrolla en paralelo estricto sin esperar al Backend.

⚡ SeamContract: POST /api/auth/google → { token: string, user: UserProfile } congela la frontera y desacopla la ejecución.

Capítulo 6: Ejecución Segura

Aislamiento en Git Worktrees y ScopeGuard

Aislamiento Físico

Pool de Git Worktrees

Cada worker opera en un subdirectorio aislado del disco, previniendo colisiones de archivos.

Contención Estricta

ScopeGuard (Deny-First)

Interrumpe inmediatamente la ejecución si el agente intenta modificar archivos fuera de su scope autorizado.

Supervisión

Process Fencing

Witness Leases y credenciales efímeras con terminación garantizada de procesos huérfanos.

Rigor Probatorio

Verificación por Evidencia: Falsabilidad Real

Paso 1 · Control Negativo

Fallo Obligatorio

El test DEBE fallar en el commit base anterior. Si pasa, se descarta por tautológico.

Paso 2 · Ejecución

Cambio del Worker

El agente genera el código en su worktree aislado bajo la supervisión de ScopeGuard.

Paso 3 · Paso en Candidato

Éxito Verificado

El test pasa en el commit candidato. Se consolida en la Evidence Matrix inmutable.

★ Criterio Popperiano: Sin control negativo previo, un test en verde no constituye evidencia válida.

Cierre del Ciclo de Vida

Integración Ascendente y Entrega Transaccional

Composición de Ramas

Fusión en Composite

• Fusión limpia de las ramas de cada hoja.
• Validación cruzada de SeamContracts.
• Reparación semántica determinista si surgen divergencias.

Garantía ACID

Fencing y Entrega Atómica

• Fencing: Verifica que la base no mutó durante la corrida.
• Fast-Forward: Entrega atómica (todo o nada).
• Recibo Inmutable: SHA de commit firmado con evidencia.

Capítulo 8: Discusión

La Frontera: Semántica vs. Control Determinista

Rol del LLM (Juicio Heurístico)

Propuesta Semántica

• Interpreta los requerimientos en lenguaje natural.
• Propone la partición modular y firmas de interfaces.
• Genera el código preliminar en cada hoja.

Rol de ManyHands (Control Formal)

Garantías Deterministas

• Audita 8 invariantes formales de compilación.
• Impone aislamiento en Git worktrees y ScopeGuard.
• Valida con Evidence Matrix y falsabilidad popperiana.

💡 Resultado Negativo: El sistema determinista no puede inventar el corte de la nada sin sugerencias semánticas del LLM. ManyHands contiene sus fallos.

Capítulo 9: Conclusiones

Tres Principios Fundamentales de ManyHands

Principio 1

Evidencia > Telemetría

Un exit code 0 no es prueba.
Solo el commit con control negativo basal es evidencia.

Principio 2

Contratos > Conversación

El diálogo libre acumula deriva.
Los tipos inmutables permiten paralelismo seguro.

Principio 3

Categórico > Scoring

Las fórmulas $C_{task}$ degeneran.
Las 3 razones discretas son explicables y robustas.
